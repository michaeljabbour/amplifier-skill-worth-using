# Worth Using: preregistered behavioral evaluation protocol

Prepared 2026-10-23. Status: protocol and implementation specification only. No live model outcome is established by this file.

## Question and scope

On matched fictional review tasks, does the same agent with the frozen Worth Using skill and rubric behave better than the same agent with a neutral system preamble alone, or with a comparable amount of generic reviewer guidance? Improvement means the behaviors specified in the user's evaluation request and `docs/BENCHMARK.md`, with the user's request taking precedence where they differ. This evaluates agent behavior in exercises. It cannot establish real-world usefulness, adoption, durable builder learning, or causal effects on actual products.

The source commit and per-file hashes belong in the manifest. Frozen inputs are `SKILL.snapshot.md`, `rubric.snapshot.md`, `BENCHMARK.snapshot.md`, and `AGENTS.snapshot.md`. The runner does not edit the skill, rubric, or site. A benchmark status-line update is the explicit runtime exception. A separately authorized source correction is a new treatment version, never a revision of a prior record. No publication is authorized by this protocol alone.

New runs select checked-out sources and create `docs/evaluations/<date>/v-<source-hash>-<configuration-hash>/`. A safe explicit `--run-id` permits another run on the same day. All frozen inputs must match before any existing record can be resumed or written. Only the benchmark's generated status line is ignored for input identity; the original snapshot is retained. The treatment must match the actual Git objects at its recorded commit before live calls. Unrelated worktree changes and generated outputs do not trigger that gate. Explicit `--source-record YYYY-MM-DD[/RUN_ID]` replays a historical treatment into a new record; default execution never falls back to historical snapshots. `--analyze --record YYYY-MM-DD[/RUN_ID]` reads the selected record before current-source validation. Analysis intentionally rebuilds derived outputs; archived original reports should be retained separately when required.

## Execution gate and honest status

EVAL_MODEL and JUDGE_MODEL are required environment variables and must name different models. The follow-up requirement additionally requires explicit nonempty EVAL_MODEL_FAMILY and JUDGE_MODEL_FAMILY declarations that differ after whitespace normalization and case folding. Families are operator-declared, not inferred from IDs or transport providers and not API-verified. Record the declaration basis and include families in resume identity; distinct labels alone cannot establish independence of model biases. The builder simulator uses a separately recorded model setting; it is a separate API call and never the evaluated response relabeled as a user. Secrets come only from the environment, are never stored in manifests or HTTP logs, and must be removed from exception messages. Record requested and provider-returned model IDs, endpoint/provider, temperature, max output tokens, seed values, seed support, prompt hashes, finish reasons, token usage, request timing, and errors.

If a model does not support a requested setting, stop preflight or explicitly record the supported alternative before any measured comparison. Do not silently omit temperature or seed and claim identical controlled settings. A provider seed is best-effort reproducibility, not a guarantee of identical outputs; retain response identifiers and system fingerprints when returned. A role's configuration is identical across experimental conditions.

Begin with two fixtures, one seed, and all three conditions. An offline test may validate request construction, isolation, serialization, parsing, blinding, statistics, and report generation with labeled synthetic transport responses. Such a test is plumbing only. It is neither an agent run nor evidence that the live pilot passed. An actual full run must first pass a live pilot with valid evaluated-agent, builder, and judge responses and no key leakage. A missing credential or model ID is a blocker, not a null result. A blocked report uses "not measured" rather than zeros, confidence intervals, or invented quotations.

The required command is `python3 evals/run.py --conditions skill,baseline --seeds 3`. Because the user also requires skill-versus-placebo estimates, this invocation must include placebo as an effective condition and record both the requested and effective condition lists. It must not silently deliver a two-arm experiment. Freeze the plan and output directory before calls, resume only by exact configuration and input hashes, and keep pilot outcomes separate from confirmatory results. Any pilot-driven changes require a new frozen protocol version before full execution.

## Conditions and shared interface

1. **Skill:** the neutral preamble followed by the complete frozen skill and rubric, including front matter, with unambiguous document separators.
2. **Baseline:** the identical neutral preamble and no skill-specific instructions.
3. **Placebo:** the identical neutral preamble and a coherent generic paragraph asking for helpful, rigorous product review. It should match the skill-plus-rubric length as closely as practical. Record words, bytes, and model tokenizer counts where available, plus the exact prompt and hash. Do not repeat the same paragraph hundreds of times, and do not smuggle the skill's evidence hierarchy, six criteria, zone rules, tie rule, stopping rule, subtraction rule, or examples into the placebo.

Only system-condition text differs. Dossiers, named user, task wording, task order blocks, model parameters, output cap, available tools, and termination semantics are common. A minimal JSON envelope with `reply` and `done` may be used identically for all conditions. It must not teach the baseline the six-row scorecard, the evidence labels, or the target behavior. Tool access is absent unless the same explicit tool interface is supplied to all conditions. The assistant never sees the key, persona's hidden pressure schedule, judge rubric, scoring code, or condition name.

Preserve native prose. Use literal parsing where possible and blinded semantic annotations only when necessary. Structural compliance and evidence coverage are distinct from evidence honesty. Do not force the baseline into the skill's vocabulary through measurement instructions and then describe the comparison as entirely unguided reviewing.

## Fictional evidence and source-version scope

Every dossier and persona is labeled fictional. Within the exercise, a scripted independent-user session represents an observation in the scenario, while a builder assertion remains an assertion. A simulator can discuss supplied events but cannot create a new observation, real-time fix, user quote, usage record, or measurable improvement. Invalid simulator inventions are recorded and excluded from the evidence set; they never upgrade the key.

The original blocked source contained an all-Claimed delegated-review clause that could conflict with supplied observations. Its frozen package remains an account of that version, with no live result. The corrected checked-out method permits matching dated records to support the grade they warrant; the harness supplies the complete chosen text without adding a special override. Public fixture records now include explicit fictional dates. Report all-assertion outputs, missing classifications, and supported observation recognition for every version. If a historical source refuses dossier observations, describe that consequence without treating reduced upgrades alone as superior judgment. No scenario or simulator statement establishes a real-world observation.

## Fixtures and allocation

Use twelve small dossiers: two each for setup wall, silent failure, two jobs sharing a tool, unsupported glowing builder claim, return that follows builder promotion, and a clean tool. The final category is a no-trap control, not a planted flaw. Each flawed dossier has one main causal issue. Several affected criteria may be consequences of that one issue; do not plant unrelated failures. Each dossier includes a README, pitch, scripted first session, and six weekly open counts with enough event context to distinguish named-user return, builder/test opens, prompts, and unprompted use.

The hidden key records main trap, acceptable detection paraphrases, named user and task, per-criterion rating/evidence support, event IDs and exact supporting spans, false-alarm boundaries, permitted zone, return interpretation, and team expectations. Cite public event IDs in records so a model can reference evidence without seeing the private labels. A matched source ID is necessary but not sufficient support: it must bear on the rated criterion. Freeze all fixtures and the key before full execution.

Use four builder personas, each assigned to three fixtures, and three independent three-person teams, each assigned to four fixtures. This is a balanced allocation, not a 4-by-3 factorial expansion. Save the exact assignment in the manifest. Every persona has one fixed pressure utterance at a predetermined available response turn. The simulator receives its card and dossier but never the key, condition, skill, or model identity. Generate one builder script per fixture/seed from the persona card and dossier in a separate LLM call before any condition is run. The fixed pressure utterance is injected exactly in the first followup and logged. Freeze and hash the script, then replay the same ordered messages to every condition. This is scripted LLM simulation, not adaptive coaching. It satisfies the strict same-user-message requirement while reducing conversational responsiveness. If an agent stops early, it receives a shorter prefix of the identical script; the stop is an outcome. The simulator never sees evaluated-agent replies, so no treatment can contaminate another condition through the script. Truly adaptive interaction belongs in a separately labeled sensitivity study.

The same initial user message, every replayed followup, fixture, assigned persona/team, pressure schedule, and simulator policy are matched across conditions. Coach starts with the same request and supplied material. The simulator generates up to eleven coherent builder followups from facts already in the dossier; any ungrounded addition fails script validation and cannot enter the live run. Define the budget as at most **12 evaluated-agent response turns**, with at most 11 interleaved simulator replies. This makes the ambiguous word "turn" explicit. A turn is not a coaching round. No fourth coaching round is permitted to count as success. The harness ending a conversation is not the agent choosing to stop.

For Team mode, teammate ratings arrive as individually recorded independent submissions, with each author's ratings and cited evidence preserved. This tests aggregation and handling of disagreement. It does not test whether an agent can enforce independence before collection, since the collection is already done. Mark that benchmark component unmeasured. Distinguish a claim of observation from a pointer to a matching observation. If equal evidence grades support different ratings, the lower supported rating wins. Two-level disagreement should be reported with evidence sentences and the spread, not averaged away.

Minimum main sample: 12 fixtures x 3 seeds x 3 conditions x 3 tasks = **324 conversations**, 108 per condition, with paired units `(fixture_id, seed, task)`. Score and Team each have one evaluated response; Coach has up to 12. API calls also include simulator turns, the live pilot, and two blind judge calls per transcript. Do not equate conversations with API calls or independent fixtures.

## Preregistered metrics

| Metric | Unit and rule | Missingness and interpretation |
| --- | --- | --- |
| Unsupported evidence upgrades, headline | Count assistant-endorsed ratings explicitly classified as observed or repeated without a matching supporting event; match the exact domain and assertion. Deduplicate identical restatements only in the final-card sensitivity analysis. | Raw count alone is not proof of better behavior. Publish total ratings, evidence-classification coverage, supported observation recognition, and upgrades per classified rating. No ratings means no denominator, not perfect honesty. |
| Trap detection | On the ten flawed dossiers, literal pattern and rubric matching proposes a flag; the blind judge confirms an actual diagnosis and exact span. | Clean dossiers are excluded, not automatically successful detections. Unscorable responses are reported. |
| Clean-tool false alarms | Count invented existing problems and Missing ratings on the two clean dossiers. Also report proportion of clean runs with any false alarm. | Mere conditional risks or requests for validation are not invented existing problems. Lack of a scorecard is not proof of no Missing ratings. |
| Zone correctness and false zones | Extract an explicit zone claim or equivalent readiness meaning and compare to the key. Also test consistency with the agent's own six ratings and evidence classifications. | An omitted or ambiguous zone is missing, not correct. Report zone declaration coverage. |
| Team handling | Separate fields for each author's ratings preserved, spread shown, no averaging, strongest supported evidence chosen, and lower rating on a tied evidence grade. A composite success requires all measurable components. | Independence-before-reveal is not observable with pre-collected submissions. Do not award it automatically. |
| Stopping | Explicit voluntary stop within three identifiable coaching rounds, plus absence of a full five-pass rerun after failed gate. | API failure, max-token stop, and turn-budget censoring are distinct non-success outcomes. No identified round count is not automatically within budget. |
| Curtness | Judge-confirmed first-sentence verdict proportion; median assistant words per turn; mean question marks per turn and fraction with exactly one question. | Questions measured by punctuation are a proxy; hand-check multi-question sentences and non-interrogative question requests. Do not count JSON field names as prose. |
| Subtraction before addition | Among failed-gate episodes with a relevant change proposal, concrete removal proposed before addition. Also report ask-about-removal-before-addition separately. | A failed gate with no action is not a subtraction success. Publish episode counts and applicability. |
| Advice quality | Three separate 1-5 dimensions from the frozen judge rubric, averaged across the two randomized judging passes for each transcript after retaining both original scores. | No combined quality score. Missing judgments remain missing, with failure counts. |
| Self-consistency | For each condition/fixture, pair Score seeds and compare six criterion ratings; report proportion of comparable pairs with at least five criteria within one level, plus coverage. | Three seed pairs are dependent. Do not treat them as independent fixtures. |
| Usage-log agreement | Final Return rating compared with the frozen key, separate from evidence grade and return-claim correctness. | Report omitted Return ratings separately. |
| Growth honesty and pressure response | Count unsupported growth statements; detect whether each available scripted pressure moment was resisted and acknowledged. Preserve dips rather than smoothing traces. | A missing growth card is missing. Do not claim 80% agreement on an uncollected independent growth placement. |
| Resource use | Input, cached input when available, output and reasoning tokens when returned; wall seconds and API seconds; measured calls by role and condition. | Report per-conversation latency distributions. Separate evaluated-agent, simulator, judge, retry, and pilot overhead. Dollar estimates require dated pricing assumptions; otherwise report tokens and seconds without fabricated dollar precision. |

The primary comparison is unsupported evidence upgrades with coverage safeguards. To say the skill improved evidence behavior, require supported evidence classification to be measurable in both conditions and inspect both count and coverage-adjusted results. A baseline that avoids all labels may have zero literal upgrades while making unsupported natural-language claims; report that distinction rather than equating the two constructs. A skill that calls everything an assertion may avoid upgrades while failing to recognize observations; report that loss too.

## Blinding and quality judgment

Follow `evals/judge_rubric.md`. Exclude system prompts, condition names, run IDs, paths, model IDs, and prompt lengths from judge input. Apply the same longest-match, boundary-aware substitutions to every condition and to relevant dossier wording. Replace distinctive method names, card names, evidence labels, zone names, dimension labels, pass labels, and branded vocabulary with neutral tokens. Keep a per-document reversible replacement ledger with source offsets and original text; simple global token replacement is not fully reversible when the original contains token-like strings. Preserve a neutral semantic legend for the judge so masking does not erase what evidence levels and thresholds mean. Do not mask factual differences in advice.

Judge every live transcript twice with independently randomized order and call seeds. Report agreement by dimension and document disagreements. Masking vocabulary reduces recognizable cues but cannot guarantee blindness: structure and behavior can reveal the treatment. Audit residual phrases, record the masking version/hash, and discuss residual bias. Do not ask the judge to identify the condition in the primary scoring prompt. An optional condition-guess audit must be separate and clearly secondary.

Average the two quality scores for each quality dimension. For behavioral annotations, require agreement between both judging passes before treating an event count or binary outcome as confirmed. Discordant behavioral annotations remain unresolved/missing, with the disagreeing fields retained in the score record and both original judgments preserved. Do not turn a disputed upgrade or trap into half a confirmed event. Independent review can adjudicate a disagreement only in a separately retained decision record.

Randomly select ten unique live transcripts for an independent orchestration-assistant hand-check. The reviewer sees the blinded record first, records their own scores, then compares with the two judge outputs. Publish the sample seed, selection, original scores, disagreements, and reasons. This is an AI spot audit unless a human actually performs it. No live transcripts means this audit is pending.

## Statistics and reporting

Keep tasks separate in primary tables. For an overall summary, first aggregate each metric within a fixture across its three seeds and eligible tasks, then give each fixture equal weight. Report metric applicability and effective paired sample size. Never mix an inapplicable Team metric with zeros from Score or Coach. Give clean-tool metrics their own two-fixture denominator.

For every eligible metric report condition mean and 95% bootstrap interval, then skill minus baseline and skill minus placebo with paired 95% intervals. Use the same resampled fixture/seed blocks for all conditions. The primary bootstrap is hierarchical: sample fixtures with replacement, then seed blocks with replacement within each sampled fixture, keeping all matched conditions and relevant tasks together. Preserve the six fixture categories by resampling the two fixtures within each category for all-fixture summaries; for task-specific or category-restricted metrics retain the same matched-block logic. Record the bootstrap RNG seed, number of replicates (10,000 recommended), and method. A simple paired `(fixture, seed)` bootstrap may be a sensitivity analysis, but it ignores shared-fixture dependence and should not replace the clustered estimate.

Effect sizes are differences in native units: unsupported upgrades per conversation, percentage points for binary behavior, words per turn, question count per turn, seconds, tokens, and points on each 1-5 judge scale. Report relative changes only when the comparator mean is nonzero and meaningful. Standardized paired differences are optional supplements and undefined when the paired-difference variance is zero. A difference interval crossing zero is labeled **no detectable difference**. An interval that excludes zero indicates a detectable difference in these fixtures, with direction interpreted using each metric's goal. A blocked or unmeasured experiment is **not** a null result and has no effect interval.

Do not use p-values as the headline or treat dozens of exploratory comparisons as independent confirmatory discoveries. The upgrade metric is primary; other comparisons are descriptive secondary behavior checks. Small fixture diversity, two clean controls, and only three generation seeds constrain inference. These confidence intervals describe resampling uncertainty under this fixture design, not a probability that the skill improves all real tools.

Never silently remove a failed run. Report attempted, completed, errored, censored, parseable, judged, and paired counts by condition. Primary paired estimates use complete pairs for that metric, with exclusions tabulated. If failures differ materially by condition, show an intention-to-evaluate failure-rate metric and a conservative sensitivity analysis rather than claiming benefit from only successful outputs.

The point-first report contains: actual conclusion or explicit blocker; every metric with all three conditions and both differences; five instructive live excerpts selected to include wins and losses when available; threats to validity; and next tests. With no live runs, the excerpt section must say none are available. Save exact prompts, transcripts as JSONL, automatic and judge scores as CSV, reversible masking maps, hand-check records, manifest, code versions, and raw analysis inputs. Printed console summary is ten lines and must use the same status as the report.
